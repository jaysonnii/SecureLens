# Security Review

## Part 1 — Review as of today

This part is AI-assisted: an automated pass over the current codebase, not a substitute for professional audit. Every finding below was independently verified against the running code — by reading it, and by reproduction or measurement for anything behavioral — not asserted from pattern-matching alone. File:line references are current as of `main` at commit `72bce8d`.

Scope: the anonymous `POST /upload` surface — rate limiting, upload handling, the reverse-proxy/tunnel topology, and the deterministic log parser and analyzer. No High or Medium findings; everything below is Low and represents residual, accepted risk rather than an active gap.

### Low

**F1 — Fixed-window rate limiter allows a ~2x burst across a window boundary.** `backend/app/services/rate_limiter.py:52-71`.
`check()` resets a client's window only when `now - window_start >= window_seconds`, where `window_start` is set at that client's *first* request — a classic fixed window, not sliding. A client that exhausts its quota right before the window ends and immediately sends another full quota right after gets roughly double the nominal rate for an instant. Verified empirically against the real `InMemoryRateLimiter` with a controlled clock: 10 requests admitted at t=0s, an 11th correctly rejected at t=59.99s, then **10 more admitted starting at t=60.00s** — 20 requests inside a ~10ms span, against a nominal limit of 10 per 60s. Bounded in impact: the burst tops out at 2x for one instant, and the request-time budget and upload-size cap (see Part 2, PR #34) independently cap what any admitted request can cost.
*Continuity:* this is inherent to the fixed-window design chosen in [PR #30](https://github.com/jaysonnii/SecureLens/pull/30), which tested per-key independence, window reset, and spoofing resistance but not this boundary-straddle case. Not a regression — a gap in the original test coverage of a deliberate design choice.

**F2 — Rate limiter state is in-process and in-memory; scaling out would silently multiply the effective limit.** `backend/app/services/rate_limiter.py:14-19`.
Confirmed by reading the current code: `_windows` is a plain dict inside one Python process, and `backend/Dockerfile:29` starts uvicorn with no `--workers` flag — one process, one replica, matches `compose.yaml`. Not currently exploitable; there's no runtime guard that would catch a *future* change (adding workers, scaling the service) from quietly multiplying the allowed rate per replica.
*Continuity:* this is not a new discovery — PR #30's own description names it explicitly under "Known limitations": *"Counters live in process memory, which suits the single-worker container in this stack. Multiple workers or replicas would each keep their own counters and need a shared store — out of scope here."* Reconfirmed still true today; carried forward as accepted risk rather than a fresh gap.

**F3 — No `Strict-Transport-Security` header.** `frontend/nginx.conf` (absent; the four headers it does set are at lines 51-54: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Content-Security-Policy`).
Confirmed by inspection. TLS is terminated upstream by Cloudflare in the documented topology, so nginx never serves plaintext HTTP to a browser and HSTS is currently moot — but nothing at the nginx layer asserts "HTTPS only" locally, so the guarantee depends entirely on what fronts the tunnel staying unchanged. No prior finding covers this; new in this review.

**F4 — No backend-side connection/read timeout independent of the reverse proxy's.** `backend/Dockerfile:29` (uvicorn `CMD`, no `--timeout-keep-alive` or equivalent flag).
Confirmed by inspection of the Dockerfile and `main.py`: uvicorn has no timeout of its own, so the only bound on a slow client that trickles bytes is nginx's `proxy_read_timeout` (default 60s) sitting in front of it. Sufficient in the documented topology (nginx is the only path in — see Part 2, PR #36) but the protection is entirely external; a backend reachable without that proxy has no self-contained defense. No prior finding covers this; new in this review.

### Verified clean

- **Command/code injection** — no `subprocess`, `eval`, `exec`, `pickle`, or YAML deserialization anywhere in `backend/app`. Upload content only ever reaches regex matching, `str.split`, guarded `json.loads`, and `csv.DictReader`.
- **Path traversal** — uploads are never written to disk under a client-controlled name. `uploads.py`'s `_read_limited_upload` keeps everything in memory; `file.filename` is only echoed back in the response, never used to build a filesystem path.
- **AI prompt boundary** — `backend/app/services/ai_summary.py:_build_ai_input()` (lines 97-128) is an explicit allowlist (`type`, `severity`, `count`, `mitre_attack`, `recommendation`, plus three top-level score fields); it never touches `evidence` (raw lines, `line_number`, `timestamp`) or any other field. Confirmed the allowlist shape is unchanged by the evidence-metadata fields PR #40 added — new fields are excluded by default because the function names what it copies, not what it excludes. The exception handler (`ai_summary.py:188-200`) logs only `type(error).__name__`.
- **Container privilege** — `backend/Dockerfile:16-18` creates and runs as a non-root user with a pinned uid; `compose.yaml` sets `cap_drop: [ALL]` on both services, `security_opt: no-new-privileges:true`, and `mem_limit`/`pids_limit`/`cpus` ceilings on both.
- **CORS** — `backend/app/config.py:94-104`: `CORS_ORIGINS` defaults to empty (fail-closed — `CORSMiddleware` is only added `if CORS_ORIGINS`) in production, and to the two local dev origins otherwise. `allow_credentials=False` is hardcoded.
- **Secrets handling** — `OPENAI_API_KEY` is read from environment, never logged (confirmed: both `ai_summary.py` failure paths log only static strings or the exception's type name), never returned in a response.
- **Debug surface** — `main.py:17-23` disables `/docs`, `/openapi.json`, `/redoc` whenever `API_DOCS_ENABLED` is false, which defaults to off in production and is also pinned `"false"` explicitly in `compose.yaml`.

### Flagged uncertainties

- **F1's real-world magnitude** was verified against the limiter class in isolation with a controlled clock, not timed against the live container with two real HTTP bursts 60 seconds apart. The arithmetic is deterministic and doesn't depend on the millisecond precision the reproduction used, so the finding itself is solid — but I haven't measured how network/scheduling jitter narrows it in practice.
- **This review's scope is narrower than a full audit** — it covers the upload/rate-limit/proxy surface because that's SecureLens's only unauthenticated, internet-facing input. It does not re-examine the frontend build tooling, CI workflow permissions, or dependency supply chain.
