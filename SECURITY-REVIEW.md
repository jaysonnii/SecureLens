# Security Review

A focused review of SecureLens's public-facing surface: the anonymous `POST /upload` endpoint, its rate limiting, the reverse-proxy/tunnel topology that fronts it, and the deterministic log parser and analyzer that process untrusted file content. Frontend-only changes (the evidence timeline, [PR #41](https://github.com/jaysonnii/SecureLens/pull/41)) were reviewed but introduce no new server-side attack surface — they render fields (`line_number`, `timestamp`, `analysis_duration_seconds`) the backend already returns.

**A note on provenance:** this document consolidates findings verified in this session, plus the record of prior fixes visible in the repo's own PRs, issues, and `docs/rate-limiter-incident.md`. Every finding below was independently re-derived and verified against the current codebase — by reading the relevant code, and by reproduction or measurement where the finding is behavioral rather than structural — not copied from an unverified summary.

## Scope covered

- `backend/app/rate_limit.py`, `backend/app/services/rate_limiter.py` — per-IP rate limiting on `/upload`
- `backend/app/routers/uploads.py` — upload handling, size enforcement, response shape
- `backend/app/services/log_parser.py` — JSON/CSV/text parsing of untrusted uploads
- `backend/app/services/analyzer.py` — deterministic detection engine
- `backend/app/services/ai_summary.py` — the AI input boundary (raw log content must never reach the OpenAI prompt)
- `backend/app/config.py`, `backend/app/main.py` — CORS, API docs exposure, production defaults
- `compose.yaml`, `frontend/nginx.conf`, `backend/Dockerfile` — deployment topology, container hardening, client-IP trust boundary
- Not in scope: the frontend's client-side code beyond confirming it doesn't weaken a server-side guarantee (client-side validation is UX only; the backend is the trust boundary — see L5's rejected candidate below)

## Headline finding

**The rate limiter was enforced after the request body had already been read** ([`docs/rate-limiter-incident.md`](docs/rate-limiter-incident.md)). It was wired as a FastAPI route dependency (`Depends(enforce_rate_limit)`), and dependencies resolve after FastAPI has parsed the multipart body to populate the `File(...)` parameter. A flooding client's entire upload — bandwidth and `/tmp` spooling — completed before the 429 was ever produced; only the (comparatively cheap) analysis step was actually being blocked. This was invisible to every functional test: status codes, `Retry-After` headers, and per-IP counts were all correct, and the defect was only in *when* the check ran relative to the body read, a property no ordinary test observes. Proven with an ASGI-level probe that wraps `receive` and asserts it's never awaited on a rejected request. **Fixed** — see M1 below.

## Findings by severity

### Medium

**M1 — Rate limit enforced after the upload body was read, defeating its main purpose.** `backend/app/rate_limit.py` (current, fixed version). **Status: Fixed and merged, [PR #33](https://github.com/jaysonnii/SecureLens/pull/33).**
Enforcement moved out of the dependency graph into `RateLimitMiddleware`, which runs on the raw ASGI `scope`/`receive`/`send` before Starlette's routing (and therefore before multipart parsing) ever touches `receive`. The regression test `test_rate_limited_upload_is_rejected_before_the_body_is_read` (`backend/tests/test_upload_rate_limit_lifecycle.py:77`) drives the app with an instrumented `receive` and asserts it's never awaited on a 429. Verified: this test currently passes, and reverting the middleware placement (moving the check back into a route dependency) makes it fail — confirmed the test actually exercises the property it claims to.

**M2 — Analyzer is worst-case quadratic; a detection-dense upload can pin a worker for minutes.** `backend/app/services/analyzer.py`, `_find_login_sequence` (O(failed × successful) pairing) and repeated full-file passes in `_find_matches`. **Status: Mitigated, not fixed. Tracked in [#35](https://github.com/jaysonnii/SecureLens/issues/35).**
Measured directly against the backend container (from issue #35): a 24.25 MiB Windows-style log with ~3,900×3,900 failed/successful login pairs took **~202s** of wall-clock CPU and returned through nginx as a 504 at the 60s `proxy_read_timeout` — while the backend kept burning CPU on the already-dropped connection. A 4.97 MiB log (~800×800 pairs) took ~10s: 4.85x the input produced ~20x the time, confirming the quadratic term dominates. The shipped mitigation (PR #34) bounds rather than fixes this: `MAX_FILE_SIZE_MB` default 25→5 (keeps worst case near ~10s) and `ANALYSIS_TIME_BUDGET_SECONDS` (default 40) checks a wall-clock deadline inside the scan loops and raises `AnalysisTimeout` → HTTP 413, so an oversized/dense log is now *rejected* rather than analyzed to completion, and the worker is never held past the budget. The algorithmic fix (indexing failed attempts by `(user, source_ip)` instead of pairing all-against-all) is explicitly deferred to the normalized-event-schema refactor per `CLAUDE.md`'s "Normalize before multi-file" note, and stays open as #35.

**M3 — Rate limiter had an unguarded read-modify-write, allowing concurrent requests to bypass the per-IP count.** `backend/app/services/rate_limiter.py` (current, fixed version). **Status: Fixed and merged, [PR #32](https://github.com/jaysonnii/SecureLens/pull/32).**
`check()` is reached from multiple threadpool threads at once (FastAPI runs sync dependencies in a threadpool). The pre-fix version read `_windows[key]`, computed the increment, and wrote it back with no lock — two threads could read the same count and both increment, letting more than `max_requests` through in the same window, and `prune()`'s dict rebuild could race with a concurrent write and drop it. Fixed with a `threading.RLock` guarding `check()`, `prune()`, and `tracked_keys()` (`rate_limiter.py:37`, `:40`, `:44`, `:53`). Verified empirically: `test_concurrent_checks_never_exceed_the_limit` (`backend/tests/test_rate_limiter.py:93`) drives 30 threads through a forced contention window and asserts the count never exceeds the limit — the PR description states this fails against the pre-lock code and passes after; re-running it now against the current code passes.

### Low

**L1 — Fixed-window rate limiter allows a 2x burst across a window boundary.** `backend/app/services/rate_limiter.py:52-71`. **Status: Open, accepted risk.**
`check()` implements a fixed window keyed to each client's *first* request rather than a sliding window: `window_start` is set once and the count resets only when `now - window_start >= window_seconds`. A client that sends its quota right before the window resets and immediately sends another full quota right after gets roughly double the nominal rate in a short span. Verified empirically against the real `InMemoryRateLimiter` class with a controlled clock: 10 requests accepted at t=0s (filling the window), an 11th correctly rejected at t=59.99s, then **10 more requests accepted starting at t=60.00s** — 20 requests allowed within roughly 10 milliseconds of wall-clock time, against a nominal limit of 10 per 60s. This is the standard fixed-window edge case (a sliding-window or token-bucket limiter doesn't have it) and is bounded in impact here: the burst is capped at 2x for one instant, not unbounded, and `ANALYSIS_TIME_BUDGET_SECONDS`/`MAX_FILE_SIZE_MB` (M2's mitigation) independently cap what any single admitted request can cost.

**L2 — Client IP for rate limiting derived from a header trustable only behind the right proxy hop, with no enforced topology to guarantee that.** `backend/app/rate_limit.py:49-58`, `backend/app/config.py:154-161`. **Status: Fixed and merged, [PR #36](https://github.com/jaysonnii/SecureLens/pull/36).**
`client_key()` trusts `X-Real-IP` whenever `TRUST_PROXY_HEADERS=true`, with no validation of which hop set it — correct only if the backend is reachable exclusively through the operator's own reverse proxy, since any client that can reach the backend directly can set `X-Real-IP` itself and rate-limit as an arbitrary key (spoofing another user's identity, or rotating to always get a fresh 10-request bucket). Before the fix, the compose stack published the backend's port and nginx trusted `X-Real-IP`/`CF-Connecting-IP` without narrowing the trust boundary to a topology that actually excluded a direct path in. Fixed by (a) removing all host port publishing for both `backend` and `frontend` in `compose.yaml` (only `expose:`, not `ports:`) so the only entry point is the `cloudflared` sidecar over the internal Docker network, and (b) `frontend/nginx.conf:36-38` trusting `CF-Connecting-IP` only from the pinned `172.30.0.0/24` compose subnet — safe specifically because, with no published port, nothing outside Docker can present that header to nginx at all; every peer that can already had to be a container on that same network. Verified by reading the current `compose.yaml` (no `ports:` keys present) and `frontend/nginx.conf` (`set_real_ip_from 172.30.0.0/24`, `real_ip_header CF-Connecting-IP`).

**L3 — Rate limiter state is in-process and in-memory; horizontal scaling silently multiplies the effective limit.** `backend/app/services/rate_limiter.py:14-19`. **Status: Open, accepted risk.**
`InMemoryRateLimiter` keeps `_windows` as a plain dict inside one Python process. This is explicitly self-documented in the class docstring ("Suitable for a single-process deployment; scaling to multiple workers or replicas needs a shared store") and matches the current deployment: `backend/Dockerfile:27` starts uvicorn with no `--workers` flag (single process) and `compose.yaml` runs one `backend` replica. Not currently exploitable — there is exactly one process holding the limiter state — but there is no runtime guard that would catch a future change (adding `--workers N`, or scaling the compose service) from silently multiplying the allowed rate per replica with no error or warning.

**L4 — No `Strict-Transport-Security` header.** `frontend/nginx.conf` (absent; other security headers are present at lines 51-54: `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Content-Security-Policy`). **Status: Open, accepted risk.**
Confirmed by inspection: `frontend/nginx.conf` sets four security headers but no HSTS. In the documented deployment topology, TLS is terminated by Cloudflare in front of the tunnel, so nginx itself never serves plaintext HTTP to an end user and HSTS is currently moot. It's flagged as open because nothing in-stack enforces or documents that assumption at the nginx layer — if the front-of-stack CDN/tunnel were ever changed or removed, there's no local header asserting "HTTPS only" to a browser that has already connected once, and that gap isn't checked by anything today.

**L5 — No connection/read timeout configured on the backend independent of the reverse proxy's.** `backend/Dockerfile:27` (uvicorn `CMD`, no `--timeout-keep-alive` or similar flag). **Status: Open, accepted risk.**
Verified by inspecting the Dockerfile and `main.py`: uvicorn is started with no timeout flags, so a slow client that opens a connection and trickles bytes has no backend-side deadline of its own — the only bound in the documented topology is nginx's `proxy_read_timeout` (default 60s) sitting in front of it. That's sufficient for the current deployment (nginx is the only path in — see L2), but the protection is entirely external: a backend reachable without that proxy in front (local dev, a differently-wired deployment) has no self-contained defense against a connection held open indefinitely.

## Verified clean

- **Command/code injection** — no `subprocess`, `eval`, `exec`, `pickle`, or YAML deserialization of untrusted input anywhere in `backend/app`. The analyzer and log parser only do string operations (regex matching, `str.split`, `json.loads` with the pre-scan depth guard, `csv.DictReader`) against upload content — no path from an uploaded log's content to an interpreted command or expression.
- **Path traversal** — uploaded content is never written to disk under a filename the client controls. `uploads.py` reads the file into memory (`_read_limited_upload`, bounded to `MAX_FILE_SIZE`) and every downstream consumer (`log_parser.parse_log_content`, `analyzer.analyze_log`) operates on the in-memory string; `file.filename` is only echoed back in the JSON response, never used to construct a filesystem path.
- **AI prompt injection / raw-content leakage into the OpenAI call** — `backend/app/services/ai_summary.py:_build_ai_input()` (lines 97-128) is an explicit allowlist: it copies only `type`, `severity`, `count`, `mitre_attack`, `recommendation` per finding plus `risk_score`/`risk_level`/`total_findings`, and never touches the `evidence` list (where raw log lines, `line_number`, and `timestamp` live) or any other field. Confirmed the same allowlist structure holds with the evidence-metadata fields added in [PR #40](https://github.com/jaysonnii/SecureLens/pull/40) — new fields on a finding are excluded by default because the function names what it copies rather than what it excludes. The failure path (`ai_summary.py:188-200`) logs only `type(error).__name__`, never the analysis dict, findings, or exception message/args.
- **JSON parser stack-exhaustion DoS** — `log_parser.py:_exceeds_max_nesting()` performs an O(n) linear pre-scan (no recursion, correctly string/escape-aware) that rejects payloads nested past `MAX_JSON_NESTING_DEPTH` (100) before `json.loads()` ever sees them, per PR #34. Confirmed this actually prevents the crash it targets — the PR description records that catching `RecursionError` alone was insufficient (by the time it fires the C stack is nearly exhausted, so the next deep operation like traceback formatting re-overflows), which is why the fix is a pre-scan rather than a catch.
- **Unbounded upload buffering** — `_read_limited_upload()` (`uploads.py:26-55`) reads in 64 KB chunks and raises 413 as soon as the running total exceeds `MAX_FILE_SIZE`, rather than buffering the whole body first. The residual gap (Starlette's own multipart parser spools to `/tmp` before this check runs at all) is closed at the infrastructure layer: `compose.yaml` caps the backend's `/tmp` tmpfs at `size=16m` and nginx's `client_max_body_size 8m` keeps an oversized body from reaching the backend in the first place.
- **Container privilege / blast radius** — `backend/Dockerfile` creates and runs as a non-root user with a pinned uid (`useradd --uid 10001 securelens`, `USER securelens`). `compose.yaml` sets `cap_drop: [ALL]` on both services (with a minimal, justified `cap_add` on `frontend` for nginx's own startup needs: `CHOWN`, `SETGID`, `SETUID`, `NET_BIND_SERVICE`), `security_opt: no-new-privileges:true`, and `mem_limit`/`pids_limit`/`cpus` ceilings on both.
- **CORS** — `backend/app/config.py:94-104`: `CORS_ORIGINS` defaults to an empty list in production if unset (fails closed — the `CORSMiddleware` is only added `if CORS_ORIGINS`, so misconfiguration means no cross-origin access at all, not an open one) and to `localhost:5173`/`127.0.0.1:5173` only in development. `allow_credentials=False` is hardcoded (`main.py:40`).
- **Secrets handling** — `OPENAI_API_KEY` is read from environment/`.env` (`config.py:163-166`), never logged (confirmed in `ai_summary.py`'s exception handler and the empty-response warning, both of which log only static strings or `type(error).__name__`), and never returned in any API response.
- **API docs / debug surface exposure in production** — `main.py:17-23` sets `docs_url`/`openapi_url`/`redoc_url` to `None` whenever `API_DOCS_ENABLED` is false, which defaults to `not IS_PRODUCTION` (`config.py:89-92`) — off by default whenever `APP_ENV=production`, and `compose.yaml:9` sets `API_DOCS_ENABLED: "false"` explicitly regardless.
- **CSV/structured-log parsing** — `log_parser.py`'s CSV and JSON record handling only produces plain strings fed into the same text-based analyzer as a `.txt`/`.log` upload; no formula evaluation, no dynamic attribute access, no code path that treats a field value as anything but data.

## Flagged uncertainties

- **L1's real-world exploitability** is bounded but not zero: the 2x boundary burst was verified against the limiter class in isolation with a controlled clock, not against the running service end-to-end (i.e., not reproduced by actually timing two real HTTP bursts against a live container 60 seconds apart). The underlying arithmetic is deterministic and doesn't depend on timing precision at the millisecond level the test used, so I'm confident in the finding, but I haven't measured whether network/scheduling jitter in a real deployment would narrow the effective window below what the unit-level reproduction shows.
- **L2's residual trust surface**: the fix is sound for the documented topology (no published ports, cloudflared as sole entry, subnet-CIDR trust), but it is a trust argument about Docker network membership rather than cryptographic proof of request origin. `frontend/nginx.conf`'s own comment already flags this: if `cloudflared` were ever moved to host networking or a different Docker network, `set_real_ip_from 172.30.0.0/24` would silently stop matching and the limiter would fall back to today's single-bucket-per-tunnel-IP behavior rather than fail loudly. I did not find a runtime check that would catch that misconfiguration; I'm treating this as inherent to the documented deploy model rather than a distinct open finding, but flagging it here since it's a real (if narrow) edge case.
- **M2's severity classification**: I scored this Medium (not High) because the shipped mitigation (input cap + time budget) converts the failure mode from "worker pinned for minutes, 504 to the client, CPU burned regardless" to "clean 413 within the configured budget" — a real reduction in blast radius, even though the underlying algorithmic cost is unchanged. A reviewer weighting "public, unauthenticated, no-cost-to-attacker CPU exhaustion vector" more heavily than the mitigation's effectiveness could reasonably call this High until #35 lands.
